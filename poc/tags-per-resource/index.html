What if tags belonged to each resource, not each page?

Three visual POCs of the same site frame, same theme, same entry format — different tag models.

The status quo

Contributors already write tags per entry in the READMEs: - [9Ghz](https://9ghz.com/) — … `type:tool` `osint` `breach`. But scripts/build_site.py flattens them: page_tags() unions every entry's tokens into the page front matter, drop_tag_tokens strips them from the entry text, and the tags plugin renders them as page-footer bubbles + a tag index that resolves tag → page.

The consequence you can see on the live site today:

  • 🔍 Clicking linux on the tag index shows you the Linux PrivEsc page — even when the tag came from one buried entry on a page whose other 25 resources are unrelated.
  • 🫕 A page with 30 resources shows one merged bubble strip — you cannot tell which resource has breach.
  • 🚫 No way to answer “give me every resource tagged firmware, wherever it lives”.
All three POCs keep the contributor workflow 100% identical — trailing backticks per entry — and change only how the build renders that data. Real repo entries are used where they exist (9Ghz, Have I Been Pwned, HackBar, impactor, mithril, Offensive-Security-AI-Models, HackTricks); sparse categories are filled with sample entries in the exact CONTRIBUTING format, labeled as such in each POC.

The three proposals

ConceptTag index becomesInteractionImplementation cost
POC 1 · Inline chips Each entry shows its own tag chips in the line (type chips get a ◆ marker). Footer bubbles deleted. tag → list of resources with category breadcrumb + anchor link into the page. None needed — static anchor links. Lowest: build_site.py keeps per-entry ownership instead of unioning; chips rendered in transform; plugin template lists entries.
POC 2 · Live filter POC 1 chips + a sticky chip toolbar on every category page; clicking filters the list in place (AND). Same as POC 1, plus each category page is self-filterable. ~60 lines vanilla JS; deep-linkable via #filter=linux+privesc. Degrades to POC 1 without JS. Low: build emits data-tags on each <li> + one JS file in the theme.
POC 4 · Tag style variations Seven visual treatments (pill, hashtag, caption, rail, outline, hover-reveal, badge-row) for the same per-entry tag markup. n/a — styling layer only. Identical markup across all seven; only CSS differs. Pure CSS swap after picking.
POC 3 · Resource catalog A new global /catalog/ page: every resource as a card (category, badges, tags) with a site-wide tag-cloud sidebar + search. The catalog is the index; the tag page collapses into it. Full cross-category filtering by tags, type, and text. Highest: extra generated page (~one template + JS index buildable from the same meta the search plugin already ships).

How they relate

They are stackable, not exclusive: POC 1 is the data-model fix (tags render where they belong), POC 2 adds page-local browsing, POC 3 adds cross-category browsing. A sensible landing zone is 1 + 2 first (they share the same emitted markup), then 3 once tag coverage across the catalog grows enough for the cloud to be useful — today only a handful of entries carry tags, so a global catalog would look thin.

Open questions if you want to adopt one: anchor-id stability when entries are renamed (reordering is fine), whether type: values should stay a separate facet (all three POCs render them distinctly) or dissolve into tags, and whether search should start accepting tag:linux query syntax (Zensical's search plugin already indexes page tags; per-resource tags would need the token kept in the entry text, which POC 1/2/3 all do).
